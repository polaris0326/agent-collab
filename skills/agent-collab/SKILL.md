# 项目协作

默认中文，只承接当前明确委托。一次安装后可在不同项目使用，不要求用户记住仓库或 ZIP。文件脚本只处理本地文件；可见聊天由宿主工具执行，两者分别报告。单 Agent 自查不能声称独立审核。

## 初始化文件

收到“初始化协作”“搭建协作环境”“init协作”或显式 `$agent-collab 初始化` 后实际执行，不只回复命令。先从当前项目上下文和 cwd 确认实际项目根并读取适用规则。Skill 安装目录、下载目录不是默认项目；无 goal 不追问，也不推导业务。

从**当前读取的本 SKILL.md 所在目录**定位 [scripts/agent_collab.py](scripts/agent_collab.py)，以实际项目根为 cwd，运行：

```text
python -B "<当前 Skill 目录>/scripts/agent_collab.py" init "<实际项目根>"
```

占位符须换成真实路径，遵守宿主 shell 规则。省略 name/goal 会复用已有参数，新项目默认目录名和空目标。不要修改用户级 Skill 来源目录。脚本安装完整项目本地 Skill，无需用户先手工 install 或重开对话。本轮来源入口已经运行 init 且有退出 0 的证据时，核实目标后直接接续，不重复文件阶段。

非 0 则报告冲突、保留文件并停止角色创建。不得删清单绕过保护。0.3.0 项目需用户明确要求升级后才运行 `upgrade "<项目根>"`（可先 `--dry-run`）；它备份原文件、保留 tasks 和段外规则，其他旧/未知版本停止。升级后先审阅旧身份、已用编号和未结责任；有旧收口职责时先在唯一任务入口明确交接，再启用新 P。不能把旧隐藏 P 转成可见就绪，也不自动终止旧角色或执行旧任务。

退出 0 后读取 `.agent-collab/project.json` 和 `.agent-collab/tasks.md`。`project.json` 的受管配置与可变 `runtime` 分开；runtime 集中保存真实角色身份。tasks 是唯一任务状态入口：本地模式维护状态，外部模式只指向已核实的权威系统；只引用角色编号。旧 tasks 中的身份文字是历史材料，不是新的活跃路由；不为迁移改写原任务。若 tasks 指向外部系统，只在该入口维护任务状态。

## 任务系统与 Projects 衔接

初始化或迁移时，先核当前委托、项目既有规则及来源项目的任务后端。用户已要求 GitHub Issues/Projects，或迁移范围包含沿用其任务管理时，须实际衔接，不能以生成 tasks.md、创建仓库或 E/P 就绪代替完整初始化。仅初始化空项目时也须核对明确约定的任务后端；没有此类约定可用本地模式，不为所有使用者强制创建 GitHub Project。

在已授权范围内查重并复用或创建目标 Project，关联正确仓库，保持要求的可见性；迁入未结任务为目标真实 Issue，保存完整需求、来源、限制及验收条件，加入看板并回读状态、责任与下一行动人。旧系统仅在授权范围内修改，不复制历史已完成任务成新待办、不把迁移登记等同于执行或接受。权限或工具缺失时明确任务管理尚未完成，不静默降级到本地。

使用 GitHub 时，Issue 保存任务事实与证据，Project 保存阶段及下一行动人；tasks.md 只保留唯一规范入口、链接和维护职责，不双写当前状态。切换前保留原记录及来源。P 在任务承接、派发、返修、审核、等待用户、接受与收尾的实际变化后及时更新对应 Issue/Project 并回读；写入失败或结果未知不记为成功。交付给出可点击看板与任务链接，核实仓库 Projects 可发现、未结项无遗漏、状态有证据。用户在 P 聊天提出需求或验收，由 P 同步，不让用户代维护看板。

### GitHub 任务标题

真实 Issue 的标题统一为 `#<实际 Issue number>｜<具体目标或交付成果>`，例如 `#3｜实现战斗结束后的奖励结算`。编号取目标仓库创建或读取回执中的实际 number，不预测下一个号，不另编 TASK 编号，也不用 Agent 编号代替。新建时先用目标名称创建，取得 number 后补齐标题并回读；创建结果未知先查原对象，不重复创建。

Project 中使用同一真实 Issue，回读 Issue 标题及看板对应项的一致性，不新建同名草稿代替。已有正确前缀不重复追加；标题前缀不一致时依据真实仓库/Issue 修正，保留目标含义。迁移到新仓库时使用目标 Issue number，原编号、原标题和来源链接保留在正文供追溯，不改写历史证据。跨仓库交流使用完整仓库名与编号（如 `owner/repo#3`）或 Issue 链接。

状态、责任与下一行动人放对应字段或 Issue 正文，不拼入标题。此规则只适用于已有真实 GitHub Issue 的任务；本地任务或未转换的草稿没有自动编号，不伪造 `#`。在 GitHub 本身显示编号的界面可能出现编号重复展示，但存储标题仍遵循上述格式。

## 可见 E/P：授权、创建与接续

目标是 **E 协作环境** 和 **P 日常伙伴** 两个用户可见入口，初始编号 E001/P001（有历史编号则继续递增），标题按下述“角色状态名称”更新。E 优先复用发起初始化的当前用户聊天并归属实际目标项目；P 为明确新建或已核实可见的本项目聊天。**不得用 `collaboration.spawn_agent` 等隐藏子 Agent 代替 E/P/T/R 的用户聊天。**

推荐用户请求：“初始化协作，当前聊天作为 E 协作环境，新建 P 日常伙伴聊天；允许本项目后续明确任务中按需创建 T/R 可见聊天及同任务通信。”这明确表达新聊天行为和可选的后续范围。Skill 本身不是授权。若真人仅说短语且宿主要求明确新聊天请求，文件阶段可先完成，然后只问一次：“是否将当前聊天设为 E、新建本项目 P，并允许后续明确任务中按需创建 T/R 可见聊天及同任务通信？”已有真人明确授权直接继续，范围按其原话；只同意 E/P 就只处理 E/P，拒绝或未答不继承额外授权。不把这道门槛扩大到只读、普通文件操作或已获准的任务转交。

1. **先查宿主与已有身份。** 发现当前实际可用的用户聊天、项目列表、读取、命名/归属、消息和等待工具，并读其参数说明。用 `list_projects` 返回的真实 projectId 核对目标路径；`create_thread` 的项目目标只能用返回的 ID。目标尚未注册或路径不匹配时，报告具体缺项，不凭空注册项目或改用 projectless 冒充归属。用可信当前聊天标识及宿主回读确认 E 的 threadId、host、项目与 cwd；不能凭标题猜“这就是当前聊天”。无法定位时 E 待核验，不能宣称整体就绪。
2. **读取 runtime 再行动。** 已有角色按 threadId/host 查证项目、cwd、可见性、责任及就绪回执，再复用。显示名、目录、编号都不能代替路由。已有 `creating` / `pending` / `unknown` 时先查原调用结果、宿主状态和返回标识，不重新调用创建。查不到或结果有歧义就保留状态，报告待核验；不能仅因列表未出现就证明创建失败。
3. **编号先预留。** 使用下述本地命令，E/P 初始化 key 可固定为 `initialization`。同 kind/key 返回同一记录；未退役 E/P 不允许再预留第二个。E 的复用与 P 的创建分别记录。编号每项目、每字母从 001 递增；已预留、失败、退役的号都不回收。升级项目首次预留该字母前，审阅旧身份历史并用 `--after <历史最大已用号>`，确认从未用过才填 0；无法查清则暂不分配。
4. **按明确授权执行可见操作。** 对已核实当前聊天命名并归属目标项目后回读 E；不能静默把另一聊天改成 E。需要新 P 时，先记 `creating`，再用宿主用户侧创建聊天 API（如 `create_thread`），目标使用已核实 projectId 与目录，标题用预留编号。启动委托只要求读项目入口/元数据/唯一任务入口、回报自身真实身份和目录并确认就绪，不执行业务、不新建其他角色或递归初始化。只创建这一条 P；不预建 T/R。
5. **立即保存实际返回，再等就绪。** 工具只返回 `clientThreadId` 时记 `pending` 的 client_thread_id；它不是 threadId，不能传给要求 threadId 的读取/消息/等待工具。通过宿主支持的创建状态或可靠回读取得真实 threadId 后才绑定；无法解析则保持 pending。调用中断或未知返回记 unknown，不重试创建。工具返回真实 threadId 也不等于就绪：读取实际项目/目录/用户可见属性，等该 P 的限定就绪回执，证据齐备才记 ready。host、project 或 cwd 未提供则保留 null/unknown，不能猜 local 或编造。
6. **交付实际状态。** 分别报告文件、E、P，并完成下述首页导航与适用项完整性核验；只在两角色均有当前宿主回读和 P 回执时称角色齐备。缺能力、缺授权、路径不明或正在创建时说明具体停点。仅初始化就停在就绪，不自动执行 goal。

### 本地身份记录命令

以下命令使用同一 Skill 脚本，cwd/目标仍为实际项目。脚本不调用 API，不证明可见性，不认证操作者填写的证据；ready 只能由宿主回读事实支持。不要直接手改 runtime 以清空计数或跳过未知状态。

```text
python -B "<Skill>/scripts/agent_collab.py" role-reserve "<项目>" P --key initialization
python -B "<Skill>/scripts/agent_collab.py" role-record "<项目>" P001 --status creating
python -B "<Skill>/scripts/agent_collab.py" role-record "<项目>" P001 --status pending --client-thread-id "<实际 clientThreadId>"
python -B "<Skill>/scripts/agent_collab.py" role-record "<项目>" P001 --status ready --thread-id "<实际 threadId>" --host-id "<实际 host>" --project-id "<实际 projectId>" --cwd "<实际目录>" --evidence "<回读与就绪回执的可追溯引用>"
```

保存宿主回读的完整实际标题可用 `--title "<编号>｜<职责或当前成果>"`；编号前缀保留，标题与回读不一致时先核对，不能声称已一致。runtime.title 是可选的历史显示快照，不要求每次改名回写，不作为路由、当前状态或验收完成条件。未知身份结果用 `--status unknown`，保留已知标识；已绑定 thread/host/project 不可替换。退役需先查未结责任、交接、未推送及本地独有证据，再 `--status retired`；此命令不归档或删除聊天/目录。替换角色用新的 key 与下一编号，旧记录保留。runtime 只存身份/生命周期，不存任务进度。不要并发初始化或修改同一元数据；这些工具不是角色服务或锁服务。

真人已明确的后续建聊天/通信授权，可在已绑定实际 projectId 的 P 记录中用 `role-record ... --authorization-source "<真人请求的可核验定位>" --authorization-scope "<实际授权范围>"` 成对保存（同命令仍须提供当前 status）。P 接续时核实该真人来源及本项目范围；Agent 转述、此 Skill 的示例或无来源字符串都不构成授权。默认两字段为 null，不从文件存在推导同意；真人撤销或缩小范围时更新来源/范围并立即遵循新输入，不沿用旧范围。不建立额外权限账本，宿主规则仍适用。

## 首页导航与交付完整性

初始化或迁移交付前，在项目 README 或已有面向用户的首页补齐一段简短协作导航；没有首页则创建最小 README。保留原内容、语言和换行约定，复用已有导航，不重复追加。文件脚本成功后由 Agent 完成此步，不以脚本退出 0 或 AGENTS.md 存在代替用户可发现入口。

导航说明日常需求与验收找当前唯一 P、环境问题找 E，T/R 按真实任务使用；链接项目规则、本地 Skill、任务规范入口和已存在的交付/验收说明。已约定外部任务后端时，还须给出已核实的看板及未结任务链接。角色实际路由只引用 runtime，阶段只引用权威任务后端，不在 README 复制维护。未就绪角色、未创建看板或尚无业务交付如实说明，不编造链接，也不为填导航创建业务或验收任务。

收尾前主动核对以下适用项，不等用户逐个发现；在现有任务或交付说明中保留固定版本、证据和未完成项，不另建并行状态台账：

- **环境与接续：** 受管文件检查、真实角色/项目/cwd 与授权、唯一收口及任务后端一致；宿主显示与磁盘/真实身份不一致时交叉核验，保留限制，不把显示值或自述当已修复。
- **入口与使用：** 首页链接可达，说明谁接需求、谁维护任务、在哪里验收；实际交付包含运行/编辑工具时，明确其真实依赖、启动方式与必要参数，不能把依赖已安装等同于默认入口能找到它。纯协作初始化不添加无关运行前提。
- **迁移与保全（仅迁移）：** 按已定范围核对代码、必要素材、许可与来源、未结需求、选中内容清单及指纹；核验必要实体/依赖和旧成果的保留或恢复依据，明确未迁入部分去向。本地保全不等于异地备份，部分复核不冒称全量重验。
- **验证与交接：** 证据对应固定候选，区分实际测试、独立审核、用户接受、推送及未测范围；按授权核远端版本和可见性。后续导航等文档变更单独记录与冻结清单的差异，不篡改旧清单冒称全文件一致。复用仍适用的有效测试，变更或新疑点才补测；不让用户重复技术核验。

发现约定范围内漏项先修复并回读；受权限、工具或未定范围限制的项目明确标为未完成及下一行动人，不静默跳过，不把“文件就绪”扩大为“整体交付完成”。

## E/P/T/R 的日常职责

- **E 协作环境**负责初始化、能力核验和环境修复。当前用户仍可在 E 对话提出任务；E 在宿主允许及真人授权内转交已记录的唯一 P，呈现结果，不自任第二个收口 P。用户也可直接进入可见 P。
- **P 日常伙伴**是唯一日常收口人，负责目标、范围、成功标准、分工、唯一任务状态和交付。短小且不会阻塞统筹的改动可自做；长时间执行、上传、扫描和持续测试交任务专属 T。消息与任务转交遵守已有通信授权，不让用户搬运内部消息；必要授权缺失则准确说明。
- **T 任务执行**在确有独立执行任务时创建可见聊天，提供明确任务与独立可写目录。**R 独立审核**用于重要改动，独立检查固定候选和证据。新的 T/R 用户聊天同样需要真人明确新聊天请求；授权可已包含在本次委托中，不能由本 Skill 或其他 Agent 来信创造。普通派发不自动变成建聊天确认。
- 每项任务只有一个状态入口和一个收口 P。角色记录集中在 runtime；任务写清目标、范围、授权、候选、验证与下一行动人。执行、审核、用户接受、合入、发布是不同事实。

接到“只读入口并确认就绪”的 P/T/R 启动请求时只做该事项；不要递归创建角色。日常委托先读当前任务及必要变化，不读长历史领取新任务。已记录路由无法核验时停止向其发业务，不以新角色静默替换。

### 多任务绑定、隔离与统筹

独立任务以权威任务入口中的目标、交付与验收范围区分；不是每条消息都新建任务。同一任务追加范围、返修和复核沿原任务处理。不同独立任务需要执行或审核角色时，各自绑定专属 T/R，不跨任务同时复用；新独立任务使用新编号/新聊天，不将旧聊天改标题后改绑。角色按实际工作和既有真人授权创建，不预建空池；短小任务可由 P 直接完成，重要改动仍须独立 R。

- **任务绑定。** 在已有 Issue（本地模式为 tasks.md 对应任务）记录收口 P、专属 T/R 编号、可写目录/分支、当前候选、验收入口、依赖及下一行动人；未创建者明确为待按需创建。角色 threadId/host/cwd 只从 runtime 查，不新增身份或进度台账。role-reserve 的 T/R key 使用稳定的真实任务标识；同项重复请求先查原记录，不重复建人。
- **未验收不释放责任。** 待审核、待用户验收、受阻和空闲都不等于任务结束。T/R 保留原任务返修/复核责任，不能接其他独立任务；用户接受后还须完成约定收尾才能标为已完成。旧聊天与证据保留，不自动删除/归档。人员确实不可用时先在原任务记录明确交接与新编号，不能冒用旧身份；R 不审核自己完成的实现。
- **新任务先判定并行。** P 核对相关未结任务、共享文件/数据、生成输出、Git 操作及发布依赖；存在冲突则在原任务入口标明依赖并排队，不让第二个写入者进入同一现场。代码执行按任务使用独立分支/工作树或明确隔离目录；不并发写主检出、共享 runtime、Git 暂存区或发布目标。合入/发布由 P 串行协调固定候选及已获授权的操作者，变更影响哪些验证就补哪些验证。
- **隔离不等于全量复制。** Git worktree 共享 Git 对象库，但通常独立检出已跟踪文件；不会自动复制未跟踪成果或缓存，LFS 实体是否展开取决于检出设置。按任务确定必要工作区，评估空间与素材范围，可用受支持的稀疏检出、按需 LFS 获取和明确只读的固定素材来源；缺资源不能记测试通过。R 纯只读审查可不建完整工作树，运行会写入时另备隔离输出/夹具。不得用共享可写素材或硬链接绕过隔离，不自动删除工作树，不为每个 Agent 全量复制大库。
- **跨任务验收。** 用户询问或接受 #A 时，P 只处理 #A 的候选和状态，不隐式暂停、取消或切换 #B。#A 的反馈需要改文件时交其专属 T/R，并先检查与 #B 的依赖；有冲突则排队并告知，不插入 #B 正在运行的执行会话。当前宿主若不能及时处理输入，如实说明排队，不能承诺 P 永远即时响应。
- **全部未结任务可见。** P 在任务承接、阶段变化、交付及用户询问进展时，从权威入口生成简短摘要，列出所有未结任务的编号/链接、阶段、负责角色、下一行动人及待用户动作，包含待排程、待验收与受阻项。逐项提供验收入口/固定候选，不能只呈现最近执行任务，也不以一项接受代替其他项接受。摘要是带本次回读时点的展示，不成为第二份可编辑状态源；无变化不增加轮询或通知。

已有项目若多个未结任务历史上共用 T/R，先保留原执行、候选与审核证据，不中断进程、不改写历史归属。P 在相关任务记录过渡：当前执行任务保留原人；其他任务的既有交付仍可独立验收，由 P 承担未结收口，发生实际返修时才按新编号专属接手、传递固定候选与证据并安排独立复核。未建立专属接手前明确标记“历史共享角色，返修待专属接手”，不能声称已完全隔离，也不为消除显示差异预建角色。跨任务共享写入现场只能在安全停点正常交接，不通过改名解决。

### 角色状态名称

用户已授权状态命名时，各 Agent 使用宿主正常改名工具更新自己的用户可见聊天，保留原角色编号和 threadId。标题格式为 `角色编号｜业务状态｜#实际任务号 简短任务名`，例如 `P001｜待你验收｜#1 项目迁移`、`T001｜返修中｜#2 配置预览`、`R001｜审核通过｜#1 项目迁移`。任务号取权威任务入口；本地任务不伪造 GitHub 编号。无当前任务用 `E001｜就绪｜协作环境`、`P001｜就绪｜日常伙伴`；P 同时管理多项未结任务时使用下述统筹摘要，数量须有当前任务依据，具体关联留在任务系统。

状态描述该角色的业务责任，不是进程运行状态：按事实使用就绪、执行中、待审核、审核中、返修中、受阻、已交付、审核通过、待你验收、收尾中、已完成。T 已交付且 R 已审核时显示“已交付”，不继续显示“待审核”；R 的“审核通过”不等于用户接受或整个任务完成。等待用户时，即使 Agent 已空闲，P 仍显示“待你验收”。收尾后 T/R 保留最后任务与已完成事实，新独立任务用新编号，不改绑旧聊天或自动退役。P 有多项未结任务时显示统筹摘要，例如 `P001｜统筹中｜1执行·1待验收·1待排程`；只列实际非零阶段数量，具体任务对应以全部未结摘要和看板为准，不仅按进程活跃数计数。

执行、审核、返修、受阻与交付中的名称由各角色在真实节点自行更新，已一致则不重复改名；恢复工作时核对当前事实，不凭旧摘要覆盖新状态。用实际 threadId 路由，禁止以标题猜身份。用户已授权项目角色状态命名且未限定只能本人操作时，P 可在用户接受且实质收尾完成后，用宿主正常工具统一更新本任务已绑定 T/R 的终态名称；只改显示名，保留编号、threadId、任务绑定和原审核结论。先核任务归属、最新状态及不存在冲突的新委托，不改其他聊天、不用“已完成”代替尚欠的工作，也不因此退役角色。

改名后可批量回读一次确认；名称同步不阻塞已记录的用户接受或已完成的业务收尾。P 不仅为终态改名唤醒空闲 T/R；只有确有待执行事项、责任交接或仍有效的本人改名限制时才通知，通知无需阻塞用户验收回执。无改名能力、回读失败或未知时明确“名称未同步”，下一次正常交互再核，不重建 Agent、不新增轮询/后台服务。runtime.title 无需逐次回写；若在必要的身份维护中更新，由 P 串行处理，不为显示快照单独提交 Git。角色生命周期 status 不随业务状态改写；当前标题以宿主回读为准、任务状态以权威任务后端为准，不承诺名称实时刷新。

## 审核、返修与收尾

P 交 R 固定完整提交 SHA，或文件清单与 SHA256，并提供当前验收标准和必要原始证据。R 独立核验，明确结论针对哪个候选，区分实测、静态审读和未测；没有独立角色时不能把自查称独立审核。

发现问题交原 T 返修，原 R 复核新固定候选；同项不另建替代聊天。用户改范围时同步受影响行动人并更新同一任务。最终交付给出成果入口、固定候选、验证/限制、待接受或待发布事项。未经授权不合入或发布。

### 主动交付与用户验收

当任务约定需要用户验收时，P 在自己的用户可见聊天中主动发出明确验收请求，不能只写“待接受”或让用户自行查任务文件。消息应提供：

- 本次请用户接受的具体范围与固定候选，以及可直接打开的成果入口。
- 与目标相称的简短检查步骤及每步预期结果；已由 T/R 验证的技术细节无需让用户重复检查，必要前提和可能写入用户数据的步骤要说明。
- 已测结果、已知限制与不在本次接受范围内的事项；若存在阻断验收的问题，先返修，不让用户替 Agent 排障。
- 明确请用户在本 P 聊天回复“接受”或描述问题，可给一句含任务编号的示例，并说明接受后做什么、哪些待办不会自动启动。

交付发生在其他角色或入口时，沿已有通信授权通知唯一 P 由其向用户交付，不要求用户搬运内部消息，也不未经授权跨渠道发送通知。请求发出后保持“待接受”；沉默、技术审核通过、已推送或用户仅问进展都不算接受。收到明确接受后，由 P 在同一任务入口记录接受范围与来源并完成已授权收尾；若反馈问题则交原 T/R 返修复核。已有明确的免人工验收或自动收尾约定按原约定执行，不额外增加确认门槛。

### 普通验收的最小收尾

用户接受的是明确任务及已交付固定候选，且没有待修复、待合入、待发布或其他约定实质工作时，按以下路径直接收尾，不机械增加“集成收尾”中间状态：

1. 窄核接受来源、范围与候选，复用仍有效的交付和审核证据；范围有歧义或候选漂移才澄清/补核。用户接受不补造测试结果，不重跑无关技术检查。
2. 在权威任务入口记录接受事实与来源。GitHub 模式优先追加简短验收记录或更新明确的当前结论区，不重复整段历史正文；随后关闭正确 Issue，更新 Project 为已完成及下一行动人。每项写入须确认成功，相关最终写入后统一回读一次 Issue/Project；支持的独立调用可并行，依赖写入按顺序执行。失败、未知或不一致先查原对象并如实报告，不盲重试，不把部分成功当全部完成。
3. P 汇总本次完成及全部剩余未结任务，及时回复用户；终态名称按上述规则非阻塞更新，已一致不重复执行。只为改名、回执或再次确认同一接受事实，不唤醒 T/R、不反复读取长历史。

默认以 Issue（本地模式为 tasks.md 对应任务）保存接受事实；固定交付文档和审核报告保留技术结论与版本，不必复制接受状态。仅因“用户接受”或标题变化，不新增本地验收文档、证据清单、runtime 写入或专门 Git 提交。已有会误导用户的“当前状态”副本应按需最小修正为指向权威入口；不改历史快照。确有交付内容修改、必要发布/未推送成果或用户明确要求仓库内验收档案时，才提交推送必要文件，并核验对应范围与远端；不跳过真实未完工作，也不把网络回读省掉。脚本不自动执行这一流程，不承诺固定耗时。

收尾按实际剩余工作核对任务、候选、职责和必要工作区；先保存可恢复的本地独有/ignored/未推送成果再考虑已获准的归档。退役编号和证据保留，不删除未知目录，不新增服务、Hook、自动角色池或隐藏 RPC。项目移动后相对文件入口仍有效，但宿主 cwd/项目归属必须重新查证。
